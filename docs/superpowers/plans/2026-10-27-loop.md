# Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Loop, a daily + practice Slitherlink page (`loop.html`): draw one closed loop along the dotted lines so every clue equals the number of its cell's sides the loop uses.

**Architecture:** Same shape as Bridges: pure, DOM-free `loop/{types,geometry,solver,generate,game,input}` modules, an SVG renderer `loop/board`, and `loop/app` handing a `PuzzleGame` definition to the shared `ui/puzzleApp` shell (routes, HUD, timer, win card, storage, analytics). Puzzles grow a hole-free region whose outline is the loop, then strip clues while the deduction solver (rules plus one-step trials) still solves the board.

**Tech Stack:** TypeScript, Vite (multi-page), Vitest (+ jsdom), Playwright. No UI framework.

**Spec:** `docs/superpowers/specs/2026-10-27-loop-design.md`

## Global Constraints

- Work on branch `feat/loop` (already created from `main`; the spec is committed there). Never `git push`.
- Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Conventional commits scoped `loop` (`feat(loop): …`, `test(e2e): …`).
- No new dependencies.
- Indexing: cells `r * size + c`; dots `r * (size + 1) + c`; horizontal edge `(r, c)` (dot `(r,c)`–`(r,c+1)`) at `r * size + c`, `H = (size + 1) * size` of them; vertical edge `(r, c)` (dot `(r,c)`–`(r+1,c)`) at `H + r * (size + 1) + c`. Cell sides: top `h(r,c)`, bottom `h(r+1,c)`, left `v(r,c)`, right `v(r,c+1)`.
- `Edge` is `0` unknown, `1` line, `2` ✕. ✕ counts as unknown for every rule.
- Presets: `small` 5×5, `medium` 7×7 (default + daily), `large` 10×10; labels Small / Medium / Large. `generatePuzzle` throws for sizes outside 5–10.
- Daily seed: `seedFromString('loop-daily:' + isoDate)`.
- Region area drawn uniformly in 35–60 % of cells; 200 consecutive failed grow tries end growth; at most 100 attempts.
- Win = every dot has 0 or 2 lines, lines form one connected loop (≥ 1 line), every clue matched. Never compared with the solution during play.
- Colours: lines/accent `#4fd6c3`, rule-break red `#ff5c7a`.
- Cell size `clamp(30px, fit, 60px)` via `ui/fit`; 10×10 fits 375 px wide; no `bestOnComputer`.
- Copy: tagline "Draw one loop. Every number counts its sides."; win title "Loop closed"; dashboard done word "Solved"; flag `loop-howto-seen`.
- Animations off under `prefers-reduced-motion` (`reducedMotion()` from `ui/fit`).
- Run `npm test`, `npm run lint` and `npx tsc --noEmit` before each commit.

## Review Focus

1. **Taps just outside the grid border** — the outer edges must be as easy to hit as inner ones; a tap 0.3 cell outside the top border picks that border edge (Task 5 test, Task 6 viewBox margin).
2. **Dragging back over a line drawn earlier in the same drag** — draw mode stays draw; the edge is applied once and stays a line (Task 5 test).
3. **`pointercancel` mid-drag** (browser takes over a touch, tab switch) — the edges painted so far are committed as one undo step, not lost and not left half-rendered (Task 5 and Task 6 tests).
4. **A second finger during a drag** — ignored; the first pointer's drag continues (Task 6 test).
5. **Dragging on a phone scrolling the page instead** — the SVG has `touch-action: none` (Task 6 test).

### Task 2: Solver

**Files:**
- Create: `src/games/loop/solver.ts`
- Test: `tests/games/loop/solver.test.ts`

**Interfaces:**
- Consumes: `geometry(size)` (Task 1).
- Produces: `analyse(size: number, clues: (number | null)[]): Int8Array | null` — the fixpoint state per edge (`0` unknown, `1` line, `2` cross), `null` on contradiction; `deduce(size, clues): (0 | 1)[] | null` — `analyse` with no unknowns left, crosses mapped to `0`, else `null`; `countSolutions(size, clues, limit): number`.

**Algorithm** (spec §5). Keep the state in typed arrays so a trial is a cheap copy.
- *Propagation* is worklist-driven: setting an edge enqueues its 2 dots and 1–2 cells; each dequeued dot/cell applies the Cell or Dot rule and may set more edges. Contradictions: cell `L > n` or `L + U < n`; dot `L > 2` or `L = 1, U = 0`.
- *Loops*: union-find over dots, unioned when an edge becomes a line, with a per-root line count. A line whose two dots already share a root closes a loop: valid only if that root's line count equals the total line count and every clue is matched (`L === n`), else contradiction. After the worklist drains, every unknown edge whose dots both have exactly 1 line and share a root becomes a cross, unless closing it would be valid by the same test; repeat propagation if anything changed.
- *Finished check*: when no unknowns remain, the state must satisfy spec §2 (in particular, zero lines is a contradiction).
- *Trials*: when propagation stalls with unknowns, for each unknown edge in index order: copy the state, set line, propagate; contradiction → set cross in the real state, propagate, and restart the plain rules. Else the same with cross → line. Stop when a full sweep changes nothing. Trials never nest.
- *`countSolutions`*: backtracking over edges in index order, pruning with the Cell and Dot rules on the partial state; at a leaf, check §2. Stop at `limit`.

- [ ] **Step 1: Write the failing tests**
  - `0 crosses its sides`: `analyse(3, clues with 0 at cell 4)` has `2` at all of `geometry(3).cellEdges[4]`.
  - `corner 3`: clue 3 at cell 0 of a 3×3 → `hEdge(3,0,0)` and `vEdge(3,0,0)` are `1`.
  - `3-3 with an unmet clue elsewhere`: 3×3, clues 3 at cells 3 and 4, 1 at cell 2 → `vEdge(3,1,1)` is `1` (crossing it would close the 2×1 rectangle early).
  - `1×1 without clues`: `deduce(1, [null])` is `[1, 1, 1, 1]`.
  - `contradictions`: `deduce(1, [0])` and `deduce(1, [2])` are `null`; `analyse(1, [2])` is `null`.
  - `two solutions stall`: `deduce(2, [null, null, null, null])` is `null`.
  - `countSolutions`: `(1, [null], 5) === 1`; `(1, [0], 5) === 0`; `(2, [null,null,null,null], 2) === 2` (stops at limit); `(2, [null,null,null,null], 100) === 13`.
  - `soundness`: for the 3×3 fixtures above, every edge `analyse` fixes agrees with every solution found by a test helper that enumerates all solutions (`countSolutions`-style backtracking collecting states).

Behaviour (spec §7): `down` → `pressed` at `nearestDot`. `move` onto a dot (`dotAt`) other than the current one → crossed edges = `walk(current, that)`; the first crossed edge of the gesture fixes `paint` (`edgeState === 1` → `'erase'`, else `'draw'`); edges are de-duplicated in order; emits `preview` with all edges so far; mode `drag`. `up` in `pressed` → `cycle` of `edgeNear` at the last point (nothing if -1); `up` or `cancel` in `drag` → `paint`. `cancel` in `pressed` → nothing.
